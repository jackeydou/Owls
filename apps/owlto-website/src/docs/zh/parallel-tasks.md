一段协调者（Router）对话可以同时把 Worker 派到多个项目。常见情况：一个仓库里改 API，接着 Web、移动端和文档跟着改。

## 开始之前

- 把涉及的每个仓库都添加为项目。见[完成第一个任务](/docs/quickstart/#第-1-步-添加项目)。
- 提交 Worker 需要看到的内容。每个 Worker 都从已提交的文件开始。

## 提出跨项目的需求

用 `@` 提到每个项目，并说明谁依赖谁：

```text
给团队邀请加一个 invited_by 字段。
1. @api-server：加字段和迁移，并在 GET /invites 中返回它。
2. 完成后，@web-app 和 @mobile-app：在邀请页面显示“邀请人”。
客户端以 API 的改动为准。
```

协调者把需求拆成任务，分别派给对应的项目。如果下一步依赖某个结果，它会等那个 Worker 汇报后再派发后续任务。后续 Worker 也可以从前一个 Worker 的分支开始，在它的基础上继续做。

在新对话里，第一个提到的项目会成为对话的默认项目。没有指定项目的任务会交给默认项目；没有默认项目时交给 Workspace。在已有对话里，提到的项目是给协调者的提示。

## 帮协调者做选择

每个项目的设置会影响协调者如何使用它：

| 设置 | 位置 | 作用 |
| --- | --- | --- |
| 描述 | 基本信息 | 帮协调者为任务挑选合适的项目 |
| 编码 Agent | 编码 Agent | 这个项目的任务由哪些智能体和模型来做，按从上到下的顺序 |
| 起始分支 | Git | 新 worktree 从哪个分支开始，例如用 `origin/main` 而不是你的当前分支 |
| 任务说明 | 任务说明 | 通用、Code Review 和 Pull Request 方面的说明，会加到这个项目每个 Worker 的提示里 |

你也可以直接在需求里说明，例如“API 任务用 Codex”或“从 origin/main 开始”。协调者派发每个 Worker 时，会传入智能体、模型、权限和起始点。

## 并行的上限

- 最多同时运行 **4 个 Worker**，另有最多 16 个排队，有空位时依次开始。
- 只有每个改代码的 Worker 都拿到自己的 worktree 时，它们才会并行。这要求项目是至少有一次提交的 git 仓库，并且**设置 → 协调者与 Worker** 中的**改代码的 Worker 并行运行**处于开启状态（默认开启）。
- 共用项目文件夹的写入型 Worker（例如在没有 git 的文件夹里）在同一项目中一次只运行一个。只读 Worker 总是可以并行。

## 跟进进度

- 按 `⌘J` 打开全景地图：所有项目和 Worker，谁在工作、谁在等待、谁已完成。在地图上按 `N` 跳到下一个等你处理的 Worker。
- Worker 完成后协调者会汇报，每份汇报都会写明分支名，方便你审阅。见[审阅并合并 Worker 的结果](/docs/review-and-merge/)。

> **注意：** 独立分支能防止 Worker 在工作时互相覆盖文件，但不能防止之后的合并冲突：如果两个 Worker 改了同一处代码，需要在合并时解决。
